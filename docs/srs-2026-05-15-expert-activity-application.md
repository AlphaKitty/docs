## 1. 引言

### 1.1 文档目的

本文档定义「专家活动申请与积分管理系统」的软件需求规格。目标受众包括产品经理、前端/后端开发工程师、测试工程师及项目干系人。文档基于原始 Excel 设计稿提取需求，覆盖专家调用、积分自提、行管审核、积分核算四大核心业务流程。

### 1.2 产品范围

**包含**：
- 专家活动申请表单（专家调用 + 积分自提）
- 基于积分大类/积分项目的字段动态显隐逻辑
- 多类型积分的差异化结构化录入模板
- 行管指派/改派专家流程
- 专家确认（接受/拒绝）流程
- 申请人评分 + 行管审核评分的双层评价机制
- 15 种积分项目的差异化计分规则
- 年度积分核算（上限封顶 + 任期折算）
- 专家详情信息展示页

**不包含**：
- 专家库的建立与维护（已有系统）
- e-HR 系统的内部实现
- 审批流程引擎的底层实现（依赖已有审批流基础设施）
- 移动端 App

### 1.3 定义、缩写与术语

| 术语 | 定义 |
|------|------|
| 专家调用 | 需求方发起申请，邀请专家参与评审、解决问题等活动 |
| 积分自提 | 专家自行提交贡献成果，申请积分认定 |
| 行管 | 行政管理角色，负责指派专家、审核评分 |
| 积分大类 | 积分的五大分类：评估评审、问题解决、成果贡献、知识沉淀、团队成长 |

| 贡献范围 | 活动影响范围（跨BG/BG内/BU内等），影响积分标准分值 |
| 标准积分 | 根据积分项目和贡献范围确定的基准分值 |
| BG | Business Group，事业群 |
| BU | Business Unit，事业部 |
| e-HR | 企业内部人力资源管理系统 |
| R&D Hub | 研发资源协调中心 |

## 2. 产品概述

### 2.1 产品背景与视角

- **业务背景**：歌尔内部建立了专家体系（17-19 级），专家需通过参与技术评审、问题解决、知识沉淀等活动累积积分以满足年度考核门槛。当前缺乏统一的申请、评价、核算系统，依赖线下沟通和手工统计。
- **系统位置**：本系统处于专家管理体系的业务中台位置，上游对接 e-HR（人员信息）、专家库（领域/标签），下游输出积分数据至年度考核/津贴发放。
- **上下游依赖**：e-HR（人员、部门、职位）、专家库（领域树、技术标签）、审批流引擎。

### 2.2 产品功能概要

1. **智能申请表单** — 根据申请类别和积分项目动态渲染字段、结构化提示模板、字段显隐规则
2. **专家调用管理** — 需求申请 → 行管指派/改派 → 专家确认 → 评价打分
3. **积分自提管理** — 专家提交成果 → 行管审核（认可/不认可）
4. **多维度积分引擎** — 15 种积分项目 × 贡献范围 × 评分等级系数的差异化计分
5. **年度核算** — 积分上限封顶、任期折算、等级门槛校验

### 2.3 产品约束

| 类别 | 约束描述 |
|------|----------|
| 技术 | 需对接 e-HR 获取人员/部门/职位信息；需对接专家库获取领域树和技术标签 |
| 组织 | 审批流程需经过承办→部门负责人→中心级负责人→R&D Hub 签批 |
| 合规 | 积分核算需支持年度审计追溯 |
| 业务 | 活动时间至少提前 1 天提交；专家任期 2 年一期 |

### 2.4 用户特征

| 角色 | 描述 | 技能水平 | 使用频率 | 关键目标 |
|------|------|----------|----------|----------|
| 需求方 | 发起专家调用申请的员工 | 一般 | 按需（项目驱动） | 快速找到匹配专家并完成评审/问题解决 |
| 专家 | 被调用或自提积分的领域专家 | 高（领域专业） | 按需 | 参与活动并积累积分通过年度考核 |
| 行管 | 行政管理人员，负责专家指派和积分审核 | 中 | 日常 | 合理分配专家资源并确保评分公正 |
| R&D Hub | 研发资源协调中心 | 中 | 低频 | 协调专家资源冲突和无人应答情况 |
| 审批人 | 部门负责人/中心级负责人 | 中 | 低频 | 审批申请并确认资源投入合理性 |

### 2.5 假设与依赖

| ID | 假设/依赖 | 类型 | 影响（若不成立） |
|----|-----------|------|------------------|
| ASM-001 | e-HR 接口可提供完整的 BG-BU 二级组织架构数据 | 依赖 | 部门带出功能不可用，需手工输入 |
| ASM-002 | 专家库已维护领域树（两级）和技术标签数据 | 依赖 | 需求领域下拉和专家匹配不可用 |
| ASM-003 | 审批流引擎已就绪，可对接本系统 | 依赖 | 需自建审批流模块 |
| ASM-004 | 专家体系分 17/18/19 三个等级，门槛分值固定 | 假设 | 门槛配置需改为可动态配置 |
| ASM-005 | 项目名称、客户代码、产品线等字段有系统统计数据源 | 依赖 | 需改为纯手工输入，无法校验 |

## 3. 需求

### 3.1 外部接口

#### 3.1.1 用户界面

系统应提供以下关键页面/组件：

1. **申请表单页** — 所有用户可见，根据申请类别和积分项目动态渲染
2. **行管待办页** — 行管角色专属，展示待指派/待审核列表
3. **专家确认页** — 专家角色专属，接受/拒绝活动邀请
4. **评价打分页** — 需求方评价 + 行管审核评分
5. **专家详情页** — 专家个人信息、专业信息、项目经历、关键贡献汇总展示
6. **专家搜索卡片** — 列表视图中的专家摘要卡片（头像/姓名/领域/标签/任期积分）

#### 3.1.2 软件接口

| 接口 | 对接系统 | 数据方向 | 协议/格式 | 频率 |
|------|----------|----------|-----------|------|
| IF-001 | e-HR | 读取 | 员工信息（工号、姓名、部门、职位、联系方式） | 表单打开时 |
| IF-002 | e-HR | 读取 | 组织架构树（BG-BU 二级） | 部门下拉加载时 |
| IF-003 | 专家库 | 读取 | 专家列表、领域树、技术标签 | 专家搜索/选择时 |
| IF-004 | 专家库 | 写入 | 专家活动记录、积分数据 | 审核通过后 |
| IF-005 | 审批流引擎 | 双向 | 提交审批 / 回调审批结果 | 流程节点触发 |
| IF-006 | 项目管理系统 | 读取 | 项目名称、客户代码、产品线、项目级别 | 项目字段加载时 [推断] |
| IF-007 | 文件存储服务 | 写入/读取 | 附件上传/预览（PDF/JPEG/PNG/Word） | 上传/查看时 |

### 5.2 JTBD 分析结果

#### 场景 1: 需求方发起专家调用

- **当（情况/触发）**：项目需要进行技术评审、人才评审或遇到技术难题需要专家支持
- **我想要（目标/期望结果）**：快速提交一个结构化的申请，填入项目信息和需求描述，系统帮我找到匹配的领域专家
- **这样我就可以（更大的目的/价值）**：减少找专家的时间成本，确保问题得到专业解决，推进项目进展
- **目前替代方案**：通过企业通讯录查找、微信/邮件联系、口头询问熟人推荐

#### 场景 2: 专家提交积分自提

- **当（情况/触发）**：专家完成了论文发表、专利申请、课程开发、知识库贡献等活动后
- **我想要（目标/期望结果）**：按系统引导填写结构化的成果描述，提交证明材料，获得相应的积分认定
- **这样我就可以（更大的目的/价值）**：累积年度积分，达到等级门槛，获得年度津贴和职业发展认可
- **目前替代方案**：年底统一填表提交，缺少过程记录，事后回忆遗漏多

#### 场景 3: 行管审核与指派

- **当（情况/触发）**：新的专家调用申请通过审批，需要分配专家
- **我想要（目标/期望结果）**：查看需求详情和需求方指定的专家，确认或调整专家分配，完成指派
- **这样我就可以（更大的目的/价值）**：合理分配专家资源，避免个别专家过载，确保领域匹配度
- **目前替代方案**：根据对专家领域的了解手工匹配，逐一确认可用性

#### 场景 4: 年底积分核算

- **当（情况/触发）**：自然年度结束，需要核算所有专家的年度积分
- **我想要（目标/期望结果）**：系统自动汇总每位专家的全年积分，应用上限封顶和任期折算规则，标记是否达标
- **这样我就可以（更大的目的/价值）**：公平准确地发放年度津贴，避免手工统计错误引发争议
- **目前替代方案**：从多个 Excel 表汇总，手工应用上限和折算规则
