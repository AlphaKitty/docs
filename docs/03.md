## **P0 地基（必须先做，否则后面全是假闭环）**

**用户故事**

1. **作为**系统管理员，**我要**维护用户与预设角色（超级管理员、领域行管、部门管理员、专家用户、普通用户、访客），**以便**与文档权限矩阵一致。
2. **作为**超级管理员，**我要**配置「领域 → 行管人员（可多人/AB 角）→ 启用状态」，**以便**申请单自动路由到正确待办人（02「3.2.1」）。
3. **作为**任意已登录用户，**我要**只看到有权限的菜单与接口返回字段（含列表脱敏），**以便**满足信息安全与角色分工（01「MTP 可查、姓名脱敏」+ 02「3.3 脱敏策略」）。
4. **作为**安全审计方，**我要**所有关键写操作留痕（谁、何时、改了什么），**以便**后续合规（02「3.2.7」可先简化为通用审计表 + 查询 API）。

**技术要点（实现时）**：替换 `permitAll`、JWT/会话、方法级 `@PreAuthorize`、前端路由 `meta.roles`、专家列表/详情按角色裁剪联系方式。

## **P1 最小业务闭环（文档「心脏」）**

**核心对象**：**调⽤申请单**（替代「只有 ProjectExpert 手工分配」）。

**用户故事**

1. **作为**普通用户，**我要**填写调⽤申请（目标领域、模式：点名/行管指派、类型：问题解决/评审/知识管理、时间区间、结构化任务描述、可选指定专家），**以便**发起正式需求（02「3.2.2」）。
2. **作为**领域行管，**我要**在指派工作台看到待办、候选人负荷/列表、改派并填写理由，**以便**完成指派（02「3.2.3」）。
3. **作为**专家，**我要**在待办里接受/拒绝并补充联系方式，**以便**闭环「专家确认」节点（01「节点3」）。
4. **作为**申请人，**我要**在任务结束后提交评价（专业/时效/态度、是否解决、附件），**以便**进入积分流程（02「3.2.4」）。
5. **作为**领域行管，**我要**看到系统预计算分、可微调分并「确认放分」或退回重评，**以便**积分正式入账（02「3.2.5」）。
6. **作为**申请人/行管，**我要**看到申请单状态与当前节点（进度条/超时标识），**以便**对齐文档「闭环管理」（01 + 02「3.2.13」可先只做简化版状态机）。

**状态机（建议最小节点）**：`草稿 → 待行管指派 → 待专家确认 → 执行中 → 待评价 → 待行管放分 → 已结项 / 已驳回`。

**刻意不做（防范围爆炸）**：飞书推送、日程冲突接口、AI 推荐——放到 P3 或单独迭代。

---

## **P1.5 专家库与审核（与 P1 可并行，但依赖 P0 角色）**

1. **作为**管理员/专家用户，**我要**单条维护专家信息并提交审核，**以便**信息变更可追踪（01「三级审批」可先简化为 1～2 级或「待审核/已通过」）。
2. **作为**HR/管理员，**我要**审核看板（队列、当前处理人、超时标红），**以便**管控入库（02「3.2.9」）。
3. **作为**用户，**我要**树形领域导航 + 多条件筛选（工号、部门、标签、学历等逐步加字段），**以便**达到规划检索能力（01「HMI + 12 条件」、02「3.2.10」——可分两 sprint）。

---

## **P2 运营与治理**

1. **作为**运营，**我要**首页/看板按领域与时间看到参与率、满意度、及时率、积分排名等（指标定义对齐 01「四、专家运营」），**以便**管理决策（02「3.2.15～17」——依赖 P1 有真实调⽤与评价数据）。
2. **作为**管理员，**我要**专家出库/恢复入库与审批，**以便**专家隐藏与合规退出（02「3.2.11」、01「出库」）。
3. **作为**管理员，**我要**Excel 批量导入与校验报告，**以便**批量入库（02「3.2.8」）。
4. **作为**专家，**我要**自主申报积分并上传举证、经审批入账，**以便**覆盖非调用场景（02「3.2.18」、01「手动积分」）。

---

## **P3 集成与增强（可选）**

1. **作为**用户，**我要**飞书消息/待办与关键节点提醒，**以便**时效（01「节点提醒」）。
2. **作为**申请人，**我要**提交前检查专家时段冲突（对接日历），**以便**减少撞期（02「检查冲突」）。
3. **作为**申请人，**我要**基于历史案例与描述获得推荐专家列表，**以便**降低选人成本（01/02「智能推荐」——规则版先做，AI 后做）。

---

## **建议的 Sprint 切法（示例）**

- **Sprint 1**：P0（认证 + 角色 + 领域行管配置 + 最小审计）。
- **Sprint 2**：P1 数据模型 + 申请单 CRUD + 行管指派 + 专家确认。
- **Sprint 3**：评价 + 预计算分 + 行管放分 + 申请单列表/详情进度。
- **Sprint 4**：P1.5 审核看板 + 检索增强（先做树 + 3～5 个高频条件）。
- **Sprint 5+**：P2 看板指标、批量导入、出库、自主积分。

## **申请链路可见性对照表（现行）**

> 说明：以接口鉴权与后端查询范围为准，前端只做按钮显隐与可用性提示。

### 列表可见性（申请链路）

| 列表 | SUPER_ADMIN | DOMAIN_STEWARD | EXPERT_USER | DEPT_ADMIN | REGULAR_USER |
| --- | --- | --- | --- | --- | --- |
| 我的申请（`/engagement-requests/mine`） | 仅自己发起 | 仅自己发起 | 仅自己发起 | 仅自己发起 | 仅自己发起 |
| 行管待办（`/engagement-requests/steward-queue`） | 全量待办（待指派+待放分） | 仅本人负责领域的待办（待指派+待放分） | 无 | 无 | 无 |
| 专家待确认（`/engagement-requests/expert-pending`） | 全量待专家确认 | 无 | 仅本人专家档案的待确认 | 无 | 无 |

### 详情页可见性（`/engagement-requests/{id}`）

后端 `assertCanView` 允许以下账号访问：

1. `SUPER_ADMIN`
2. 申请人本人（`applicant`）
3. 该单所属领域行管（`domain steward`）
4. 被指派专家的 owner（专家本人）

### 详情页关键动作可见性

| 能力项 | 可见角色 | 额外条件 |
| --- | --- | --- |
| 草稿编辑/提交 | 申请人 | 状态 = `DRAFT` |
| 行管指派 | `DOMAIN_STEWARD` / `SUPER_ADMIN` | 状态 = `PENDING_STEWARD_ASSIGN` |
| 改派专家 | `DOMAIN_STEWARD` / `SUPER_ADMIN` | 状态 = `PENDING_EXPERT_CONFIRM` 或 `IN_PROGRESS` |
| 专家确认（接受/拒绝） | `EXPERT_USER` / `SUPER_ADMIN` | 状态 = `PENDING_EXPERT_CONFIRM`；非超管时必须是被指派专家 owner |
| 评价提交（含附件上传） | 申请人 | 状态 = `IN_PROGRESS` |
| 行管放分（可参考建议分） | `DOMAIN_STEWARD` / `SUPER_ADMIN` | 状态 = `PENDING_STEWARD_SCORE_RELEASE` |
| 退回重评 | `DOMAIN_STEWARD` / `SUPER_ADMIN` | 状态 = `PENDING_STEWARD_SCORE_RELEASE` |
| 查看评价附件 | 申请人 / 领域行管 / 指派专家 owner / `SUPER_ADMIN` | 后端 `assertCanView` 校验 |
